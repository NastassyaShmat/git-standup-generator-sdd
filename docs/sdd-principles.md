# SDD Principles — Core Concepts of Spec-Driven Development

Reference document for the comparative SDD study. Covers 7 foundational principles with
per-methodology analysis. Sources: Spec Kit (github/spec-kit), OpenSpec (Fission-AI/OpenSpec),
Kiro (kiro.dev), BMAD (docs.bmad-method.org).

---

## 1. Spec-First Execution

**Definition.** Work begins with a written specification, not with code. The spec defines
*what* to build and *why* before any technical decisions are made. Implementation is a
downstream artifact of the spec, not its precondition.

**Core idea.** Traditional development treats specs as scaffolding that gets discarded once
"real work" begins. SDD inverts this: the specification *is* the primary artifact; code is its
output. This prevents the most common failure mode in AI-assisted development — vague prompts
producing unpredictable results.

**In Spec Kit.** Enforced structurally. The CLI prevents task generation and implementation
until `spec.md` and `plan.md` are complete. The workflow makes spec-first the only path:
`/speckit.specify` → `/speckit.plan` → `/speckit.tasks` → `/speckit.implement`. The
`/speckit.implement` command validates prerequisites (constitution, spec, plan, tasks) before
executing a single line.

| Methodology | Spec-First Execution |
|-------------|----------------------|
| **Spec Kit** | Hard enforcement. Implementation command validates prerequisites; no skipping phases. |
| **OpenSpec** | Soft encouragement. `/opsx:propose` scaffolds artifacts together, but `/opsx:apply` has no execution gate and can run at any point. |
| **Kiro** | Mandatory for Feature Specs. IDE workflow begins with requirements or design, never with code. |
| **BMAD** | Mandatory. A planning track (Quick Flow, BMad Method, or Enterprise) must produce planning documents before the developer agent is invoked. |

## 2. Structured Artifact Hierarchy

**Definition.** SDD organizes documentation into a layered stack of distinct artifact types,
each with a defined scope and lifespan. Layers are ordered from high-level intent down to
concrete tasks.

**Core idea.** A flat spec document conflates concerns and breaks down quickly for real features.
A hierarchy lets each layer answer a different question:

- *Principles layer* — what values and constraints govern all decisions?
- *Requirements layer* — what should the system do (observable behavior)?
- *Design/plan layer* — how will we build it (technology, architecture)?
- *Tasks layer* — what are the concrete, ordered implementation steps?

Keeping layers separate allows targeted revision: changing a design decision doesn't invalidate
requirements; adding a task doesn't require re-specifying behavior.

**In Spec Kit.** Five layers:
1. `constitution.md` — governing principles, coding standards, constraints (project-wide)
2. `spec.md` — user stories and functional requirements (per feature)
3. `plan.md` — tech stack, architecture, implementation approach (per feature)
4. `tasks.md` — ordered task list with dependency markers (per feature)
5. Source code — generated by `/speckit.implement`

| Methodology | Artifact Hierarchy |
|-------------|-------------------|
| **Spec Kit** | 5 layers: `constitution.md` → `spec.md` → `plan.md` → `tasks.md` → code. Strictly sequential, per-feature. |
| **OpenSpec** | 4 layers per change: `proposal.md` (why) + `specs/` delta (what) + `design.md` (how) + `tasks.md` (steps). Plus a persistent `openspec/specs/` as system-level source of truth. |
| **Kiro** | 3 layers per spec: `requirements.md` → `design.md` → `tasks.md`. Optional `bugfix.md` replaces requirements for bug workflows. Minimal, per-spec. |
| **BMAD** | 5+ layers: `PRD.md` → `architecture.md` → `epics/` → individual story files → `sprint-status.yaml`. Role-stratified: PM, Architect, and Developer each own distinct layers. |

## 3. Human-AI Alignment Gate

**Definition.** Before implementation begins, the human and AI must explicitly agree on what
is being built. The specification serves as the artifact of that agreement — a checkpoint where
intent is made explicit and ambiguities are resolved.

**Core idea.** AI coding assistants are powerful but probabilistic. Without explicit alignment,
an AI will infer intent from context and optimize for plausibility rather than correctness.
The alignment gate transforms implicit assumptions into written commitments that both parties
can reference and challenge. The gate does not have to be a hard block — it can be a workflow
step — but it must exist.

**In Spec Kit.** Multiple explicit gates built into the workflow:
- `/speckit.clarify` runs structured coverage-based questioning and records answers in the spec.
- The **Review & Acceptance Checklist** within `spec.md` is explicitly validated before planning.
- `/speckit.analyze` checks cross-artifact consistency after tasks are generated.
- Human reviews and can refine at each phase transition.

| Methodology | Human-AI Alignment Gate |
|-------------|------------------------|
| **Spec Kit** | Explicit, multi-stage: `/speckit.clarify` (structured Q&A), acceptance checklist in `spec.md`, plan audit, and `/speckit.analyze` before implementation. |
| **OpenSpec** | Implicit. Human reviews artifacts before running `/opsx:apply`, but there is no enforced checklist or blocking step. |
| **Kiro** | Built into the IDE. Requirements are generated from a natural language prompt and iterated with the human; phase transitions (Requirements → Design → Tasks) require explicit user confirmation. |
| **BMAD** | Strongest post-planning gate: `bmad-check-implementation-readiness` validates cohesion across PRD, architecture, and stories before the developer agent begins implementation. |

## 4. Requirements-to-Code Traceability

**Definition.** Every implementation task is explicitly linked to a requirement or user story.
Changes to code can be traced back to the spec that motivated them; missing coverage can be
detected by comparing the task list against requirements.

**Core idea.** Traceability prevents two failure modes: (1) *orphaned code* — implementation
that no requirement motivated, often introduced by an overeager AI; (2) *uncovered
requirements* — spec items that were never implemented. It also supports post-implementation
validation: "does the code do what the spec said?"

**In Spec Kit.** `tasks.md` is generated directly from `spec.md` and `plan.md`; tasks are
organized by user story and include file paths and test steps. The `/speckit.analyze`
command explicitly checks cross-artifact consistency and coverage. Community extensions
(e.g., `spec-kit-verify`, `spec-kit-verify-tasks`) automate detection of phantom completions
and spec drift.

| Methodology | Requirements-to-Code Traceability |
|-------------|----------------------------------|
| **Spec Kit** | Tasks organized by user story; `/speckit.analyze` checks cross-artifact coverage; community `spec-kit-verify` extensions detect phantom completions and spec drift. |
| **OpenSpec** | Delta specs in change folders track what changed per requirement; on archive, deltas merge into the system-level source of truth, preserving an auditable history. |
| **Kiro** | Tasks derived directly from EARS requirements, making coverage implicit in the generation step. Real-time task status tracking in the IDE per task. |
| **BMAD** | Epic → story → `sprint-status.yaml` chain. Each story file references its parent epic, which references the PRD, creating full lineage from business requirement to implemented story. |

## 5. Iterative Refinement Before Commitment

**Definition.** Specifications are not written once and treated as final. SDD workflows include
deliberate refinement phases — structured questioning, cross-artifact review, plan validation —
before implementation begins. The goal is to front-load ambiguity resolution rather than
discover gaps mid-implementation.

**Core idea.** One-shot code generation from a single prompt trades planning cost for
implementation rework. SDD accepts slightly higher upfront cost in exchange for substantially
lower rework. The key word is *deliberate*: refinement has a defined scope and exit condition,
rather than being open-ended iteration.

**In Spec Kit.** The most explicit refinement protocol of the four:
- `/speckit.clarify` — structured, sequential clarification that fills a Clarifications
  section in the spec. Recommended before planning.
- `/speckit.checklist` — generates custom quality checklists that validate completeness and
  clarity of requirements ("unit tests for English").
- Plan validation step — after generating `plan.md`, the human explicitly audits it for
  gaps and over-engineering before tasks are generated.
- `/speckit.analyze` — cross-artifact consistency analysis after task generation, before
  implementation.

| Methodology | Iterative Refinement Before Commitment |
|-------------|---------------------------------------|
| **Spec Kit** | Most structured: dedicated `/speckit.clarify` step, `/speckit.checklist` validation, plan audit, and `/speckit.analyze` consistency check — all pre-implementation, each with a defined scope and exit condition. |
| **OpenSpec** | Most flexible: explicitly "iterative not waterfall". No phase gates; any artifact can be updated at any time. Continuous refinement with no enforced order. |
| **Kiro** | Two workflow variants — Requirements-First (requirements drive design) and Design-First (technical design derives requirements) — with explicit iteration between phases before task generation. |
| **BMAD** | Widest pre-planning toolkit: optional workflows for brainstorming (`bmad-brainstorming`), market/domain/technical research, product brief, and PRFAQ — all available before the PRD is written. |

## 6. Context Persistence Through Artifacts

**Definition.** Spec artifacts serve as durable, queryable memory for AI agents across sessions
and context resets. They replace ephemeral chat history as the authoritative source of project
intent, decisions, and constraints.

**Core idea.** AI agents have finite context windows. Conversations expire; context windows get
crowded; sessions reset. Without persistent artifacts, every new interaction starts from zero
and the AI re-infers project intent from code alone. Spec artifacts externalize the decisions
that should not be re-derived on each interaction: project principles, agreed requirements,
technical choices, and in-progress task state.

**In Spec Kit.** The `constitution.md` file in `.specify/memory/` is explicitly loaded as
persistent context by the AI agent across all phases of all features. The CLAUDE.md
(or equivalent per-agent file) is updated automatically to include references to active spec
artifacts. This makes the constitution a standing directive — not a one-time prompt.

| Methodology | Context Persistence Through Artifacts |
|-------------|--------------------------------------|
| **Spec Kit** | `constitution.md` in `.specify/memory/` loaded as persistent context across all phases and features. `CLAUDE.md` (or equivalent) updated automatically to reference active spec artifacts — constitution acts as a standing directive, not a one-time prompt. |
| **OpenSpec** | `openspec/specs/` is the living system-of-record for the entire codebase, updated on every archived change. "Context hygiene" is an explicit usage guideline: clear context before implementation so spec artifacts — not conversation — provide ground truth. |
| **Kiro** | Steering files (`.kiro/steering/*.md`) injected into every agent interaction as persistent context, separate from per-feature spec artifacts. |
| **BMAD** | `project-context.md` + BMAD planning outputs under `methodologies/bmad/_bmad-output/` accumulate across sessions. Each workflow runs in a fresh chat, but prior workflow outputs provide continuity. |

## 7. Separation of What/Why from How

**Definition.** Requirements documents describe observable, implementation-agnostic behavior
(what the system does and why it should do it). Design/plan documents describe the technical
approach (how it will be built). These concerns are kept in separate, explicitly typed
artifacts.

**Core idea.** Conflating "the system shall authenticate users" with "we'll use JWT with RS256,
stored in Redis" in a single document makes requirements brittle: changing the implementation
invalidates the requirement document, even though the user-facing behavior is unchanged. Clean
separation allows requirements to remain stable across technical refactors and lets architectural
decisions be revisited without re-specifying behavior.

**In Spec Kit.** Enforced by command structure: `/speckit.specify` explicitly instructs the
user to *not* mention tech stack — focus on *what* and *why*. `/speckit.plan` is the first
point where tech stack and architecture are introduced. `spec.md` and `plan.md` are separate
files with separate templates, and the workflow enforces the ordering (spec before plan).

| Methodology | Separation of What/Why from How |
|-------------|--------------------------------|
| **Spec Kit** | Enforced by commands: `/speckit.specify` prohibits tech stack; `/speckit.plan` is the first point for architecture. Separate file templates and enforced ordering make the boundary structural. |
| **OpenSpec** | Most explicit by definition: `spec.md` is a *behavior contract*; concepts docs list what must not appear in it (class names, library choices, implementation steps). Implementation details belong exclusively in `design.md` or `tasks.md`. |
| **Kiro** | `requirements.md` captures observable behavior in EARS notation; `design.md` covers architecture, sequence diagrams, and data flow. Design-First variant allows the reverse flow for technically-constrained projects. |
| **BMAD** | PRD (product requirements, user needs) vs. architecture document (technical decisions, component design, infrastructure). Separation institutionalized through distinct agent roles: PM writes the PRD, Architect owns the architecture. |

## Summary

All four methodologies share the same underlying insight: writing specifications before writing
code reduces ambiguity, prevents AI from optimizing for the wrong target, and creates an
auditable record of intent. They diverge on three axes:

**Strictness.** Spec Kit and BMAD enforce phase gates; OpenSpec deliberately removes them;
Kiro sits in between with IDE-native phase transitions.

**Scope.** Spec Kit and OpenSpec treat specs as a system-level artifact (all features
accumulate in one spec store); Kiro and BMAD treat each feature/epic as a self-contained spec
unit.

**Tooling coupling.** Kiro is the most coupled to a specific environment (Kiro IDE / VS Code);
BMAD is coupled to its own agent framework; Spec Kit and OpenSpec are agent-agnostic and work
with 20+ tools.
